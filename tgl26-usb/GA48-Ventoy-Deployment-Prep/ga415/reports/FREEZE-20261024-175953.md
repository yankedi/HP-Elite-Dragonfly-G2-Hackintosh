# 2026-10-24 17:59:53 freeze: kernel divide-by-zero identified

## Finding

The recovered panic and the independently decoded NVRAM panic agree exactly.
The immediate crash cause is a CPU integer divide by zero in the Apple TGL
accelerator's IOSurface device-cache allocation calculation. The panicked task
is `AvatarPickerMemojiPicker`, PID 2732. This is a kernel panic, not merely a
WindowServer rendering stall or an SSH authorization failure.

The precise reason that the IOSurface plane metadata reached this calculation
with a zero divisor still needs ABI/input validation. No fix was applied or
tested during this investigation.

## Why the apparent 2020 timestamp was misleading

The new diagnostic is named
`/Library/Logs/DiagnosticReports/Kernel-2020-01-01-080122.panic`.
Its header and file times use 2020-01-01. It was absent from the real pre-freeze
17:42 health inventory. The existing `.contents.panic` changed from 4757 bytes
to 7505 bytes; the newly appearing panic file is 7592 bytes. Therefore looking
only for files with current-date mtimes would miss this crash.

## Exact fault

```text
panic(cpu 6 ...): Kernel trap at 0xffffff7f96718bcd,
type = 0=divide error
Panicked task ... pid 2732: AvatarPickerMemojiPicker
IGAccelResource::calculateIOSurfaceDeviceCacheVRAMBytes + 0x399
R15 = 0; RAX = 0; RDX = 0
```

The backtrace traverses:

```text
IOAccelSharedUserClient2::new_resource
  -> IOAccelResource2::newResourceWithIOSurface
  -> IOGraphicsAccelerator2::deviceCacheForIOSurface
  -> IOAccelResource2::newResourceWithIOSurfaceDeviceCache
  -> IGAccelResource::calculateIOSurfaceDeviceCacheVRAMBytes
  -> div r15d (R15D == 0)
```

The exact donor UUID is `BA3AA1C0-FE6B-33B3-9D85-73F848394E3D`.
Its preserved binary SHA256 is
`14e21de55f2923c3c46a33731ab2f7a71e1baf472f88d1fd8c702e821c171393`.
Using the panic's loaded driver base:

```text
0xffffff7f96718bcd - 0xffffff7f966a6000 = 0x72bcd
function start = 0x72834
0x72bcd - 0x72834 = 0x399
0x72bcd: 41 f7 f7    div r15d
```

This confirms division by zero rather than quotient overflow. The panic reports
normal compressor/swap state and `System shutdown begun: NO`.

## Plane-metadata path and existing source

The preserved donor function reads `[IOSurface + 0xb0]` at `0x7287d`, stores the
value as a planar-path flag at `[rbp - 0xdc]`, and takes the branch containing
`div r15d` when that flag is nonzero. No zero-divisor guard precedes this exact
division. The function contains both IOSurface plane-accessor and dictionary
metadata paths; the panic does not preserve enough stack/object data to establish
which metadata producer supplied the zero value.

The already published source
`GA414-Native-NOAUX-Source/src/NootedGreen/kern_gen11.cpp:2407–2414`
documents an upstream `xe/planes` crash at this exact `0x72bcd` instruction.
Its candidate `XE-PLANES2` replacement is defined/applied at lines 2245–2262,
and is explicitly disabled by `-ngreennoplanesfix`.
That disabling flag is present in both the recovered panic boot arguments and
the current R6 boot arguments.

The source's proposed `+0x98` field is documented there for a different Tahoe
build, 25G241. Its correctness for the actual 25G83 IOSurface implementation and
multi-plane resources has not been established here. Neither removing the flag
nor forcing every IOSurface to non-planar is a verified fix. The latter also has
documented multi-plane/YUV regressions in the source comments.

Next focused investigation: verify the actual 25G83 IOSurface plane-count and
per-plane accessor ABI against this donor, then assess a narrowly scoped
metadata/validation correction. Keep this allocation-time panic separate from
the already captured B/C silent-pixel errors and from the verified NOAUX fix.
