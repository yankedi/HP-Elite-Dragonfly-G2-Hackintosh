# Author-recommended upstream control: preparation

Status update, 2026-10-29: **superseded by the [graphics subtraction plan](GRAPHICS-SUBTRACTION-PLAN.md)**. The delivered clean BASE was reported stuck at verbose boot. Its recovered OpenCore log records NootedGreen prelinked injection failing with `Invalid Parameter`; this was not a valid running clean-upstream comparison. The preparation details below describe the earlier offline state, not current acceptance.

## Source and compatibility gate

The [maintainer's reply on issue #19](https://github.com/JulioNectar/Hackintosh-XPS13Plus-IrisXe-Tahoe/issues/19#issuecomment-6456141350) recommends a same-machine, same-OS trial of the current repository version without our local patches, with `ngreen-eu=80 ngreen-l3=6`. On 2026-10-28, the repository HEAD inspected was [`562e02ca4a207414dd849ea0c573d826f86b4901`](https://github.com/JulioNectar/Hackintosh-XPS13Plus-IrisXe-Tahoe/commit/562e02ca4a207414dd849ea0c573d826f86b4901). Pin the actual source and artifacts used at test time; HEAD may move.

**Important mismatch:** that revision's `install.sh` requires macOS 26.7.1 / `25G241` by default. Our last documented control used 26.6.2 / `25G83`. The script refuses another build unless forced. Do not interpret a forced run as tested compatibility. Ask the author which upstream revision or controlled method is appropriate on 25G83 before replacing system components. Updating macOS would change the same-OS comparison and requires its own decision.

The installer is not a NootedGreen-only replacement: it builds and installs graphics kexts, HookCase, graphics bundles, a Metal driver and shader compiler; the nested installer replaces existing paths, modifies a kext plist and invokes `kmutil`. A separate EFI cannot by itself revert shared `/Library` or kernel-collection changes. `--build-only` still requires a compatible macOS environment and dependencies; no installer mode has been run here. Inspect both [install.sh](https://github.com/JulioNectar/Hackintosh-XPS13Plus-IrisXe-Tahoe/blob/562e02ca4a207414dd849ea0c573d826f86b4901/install.sh) and [macos/install-macos.sh](https://github.com/JulioNectar/Hackintosh-XPS13Plus-IrisXe-Tahoe/blob/562e02ca4a207414dd849ea0c573d826f86b4901/macos/install-macos.sh) before any approved installation.

The requested comparison is the **current JulioNectar repository source without this HP project's additional patches**, not simply a build of unmodified `sgiammori/NootedGreen@95f81898`. The installer pins that latter project for its dependencies, while building the JulioNectar repository's own source. Record both identities separately.

## Offline build result

An isolated checkout of author commit `562e02ca4a207414dd849ea0c573d826f86b4901` was cross-compiled on the development host with the existing Linux helper and locally retained dependencies. The tracked `src` tree had no changes against that commit. The resulting x86_64 NootedGreen executable SHA-256 is `c822255c655af62fdf0d934dd5d985e6651f541e18541c3ef78122b57af0463c`.

The original build was unsigned. Subsequently `rcodesign` 0.29.0 generated ad-hoc signed copies for the baseline and each group. Its `verify` command returned the same CMS error previously recorded for both the GA416 binary and a native-verified GA414 baseline; CMS is not required for an ad-hoc signature. The same independent GA416 code-directory audit was then run against all eight new bundles: SHA-1 and SHA-256 code pages and special slots passed, and deliberate corruption of the executable, Info.plist and CodeResources was rejected. Each image readback matched its audited bundle. Native macOS signature validation and loading of these new binaries remain unverified. The Linux wrapper is not the author's macOS `zsh` build, and neither equivalence to that build nor 25G83 compatibility or runtime loading has been established. The private local builds, modified helper, logs and hashes are retained outside this public tree.

The current source parses `ngreen-eu=80` as 10 subslices and accepts even L3 values 2–16. Its Raptor Lake byte-patch group has a `!isRealTGL` gate, whereas the `getGPUInfo` route has different conditions; native-TGL effects must be checked at runtime rather than inferred from the RPL path.

Seven independent **source-level experimental groups** have since been ported to this pinned author revision and cross-compiled: AUX, CCS, PLANES2, R2, R3, R5+L3=6 and R6. Each has a separate contextual diff and unsigned binary; they are not cumulative or runtime-verified. The new AUX, CCS and PLANES2 ports require review against the historical implementation, actual patch-hit evidence and runtime testing. R5 changes the topology path and must be interpreted separately from the upstream boot-argument path. Historical PLANES2 on GA415 was enabled by a configuration change, not a newly authored GA415 source patch.

Eight private independent disk images have been generated: the clean author-source baseline and seven single-group variants. They use the GA419 OC baseline, preserve its existing boot arguments and add `ngreen-eu=80 ngreen-l3=6`. OpenCore 1.0.8 `ocvalidate`, FAT filesystem checks and full image-file readback passed. They have not been booted or written to USB. They rely on the system's already-installed graphics stack rather than an installation of the author's entire current stack. User requested proceeding on the existing OS despite the build mismatch; the mismatch remains relevant when interpreting results. System-component recovery and actual signature/loading remain unverified. Exact private paths, hashes and collection steps are in the local operational handoff.

## Baseline and experimental design

1. Preserve the existing private GA419 accelerated EFI, GA420C basic-display EFI, and their tested artifact hashes. Record the actual current OS, boot session, installed graphics stack and hashes afresh; older captures are not proof of current state.
2. Prepare an independent boot candidate only after validating source, required dependencies and system-build compatibility. Record exactly which boot arguments, kexts, system bundles and kernel collections differ. Do not assume changing only NootedGreen reproduces the author's full installation.
3. Before any system modification, establish and verify a recovery path covering both EFI and every shared installed graphics component, including the previous kernel-collection state. A candidate EFI or historical backup alone is not verified recovery of system-level modifications. Hardware writes, boot changes and restarts require separate explicit authorization.
4. At the trial, verify the loaded binary identity, effective EU/L3 settings, the attached framebuffer and accelerator, OS build, boot session, and all relevant loaded component identities. Start off-machine unfiltered capture with an explicit same-boot guard and bounded disk-space monitoring. Preserve logs privately; review/redact before sharing.
5. If a panic occurs, retain the full native report or firmware-variable recovery, original hashes, exact uptime and precise configuration. The author's suggested ~5-minute checkpoint is useful, but surviving it does not prove stability; continue a separately defined observation window and record workload.
6. Only after the upstream result, evaluate local changes in individually controlled groups, prioritizing the author's CCS/AUX hypothesis while recording all dependencies and exact deltas. A successful or failed group trial identifies an association, not automatically the first corrupting write.

The prior GA419 panics and GA420C observation remain described in [GRAPHICS-STABILITY.md](GRAPHICS-STABILITY.md). The `pmap_recycle_page` signature is a detection point consistent with a page still referenced at recycling; the source of any stale mapping or memory corruption remains unproven.

The private GA419 OC archive was re-hashed during preparation and matches its recorded SHA-256 `2061a02a7a2e724b94d3162c77a45b7f1adac72054e4777bf0fd0145566dca4f`. It is an OC archive, not a standalone disk image and not a complete backup of the macOS-installed graphics stack. The archive's original build report was written before boot; later GA419 runtime evidence documents actual accelerated trials. The accelerated baseline's [loaded-kext inventory](../evidence/accelerated-loaded-kexts.txt) contains NootedGreen, TGL components and HookCase; their current live state cannot be inferred from that historical capture.

The upstream [issue #3](https://github.com/JulioNectar/Hackintosh-XPS13Plus-IrisXe-Tahoe/issues/3) concerns visible rendering artifacts on an i5-1334U system, rather than an independently established fix for this HP's pmap panic. Upstream documentation describes `xe-topo` as `(EU << 8) | L3`, so 80 and 6 encode as decimal `20486`; treat that as a configuration/driver report, not by itself proof of a live fuse read or GPU stability.
